# Native Qwen port and validation

The runtime vendors only Qwen3TTS and its codec prerequisites from `Blaizzy/mlx-audio-swift` commit `01dec7c9bdce3088a6b6b7ab9f2e403458195efb` (MIT), rather than linking all of MLX-Audio's models. The official algorithm/reference repository is QwenLM/Qwen3-TTS at `022e286b98fbec7e1e916cb940cdf532cd9f488e`. Swift package pins are MLX 0.31.4, MLX-LM 3.31.4 and Transformers 1.3.4: a compatible set verified on this Mac. This replaces the old 0.32.2-only Fish dependency graph.

Chatter modifications:

- Local-only model loading; no runtime repository download or deletion of damaged directories. Installer verifies immutable file hashes separately.
- Missing tokenizer, codec or speaker weights fail visibly instead of using uninitialized components.
- Synchronous generation on the dedicated engine worker; external cancellation checked per frame; throwing chunk callback propagates disk and cancellation failures.
- Logs use stderr; stdout is exclusively the engine JSON protocol.
- A generation that reaches its frame budget without EOS throws `AudioGenerationError.frameBudgetReached` rather than returning clipped success (see also the 3.4.0 section below: the engine now follows each passage and rarely waits for the budget). The bound is larger than the upstream text heuristic (max(75, tokens × 6)): max(128, tokens × 12) frames, capped at 2,048 per passage. The engine generates such a passage again, up to three attempts, before failing the job; 3.3.1 lowered the floor from 256 frames so a run-on is caught in half the time.
- `DecoderBlockUpsample.step` holds its overlap without the transposed conv's bias, which the next chunk's first positions already carry. Upstream adds the bias twice there, at every streamed chunk boundary (each 0.8 s in Responsive). On a test decoder, streamed chunks now join to the whole decode within float tolerance; on the installed codec the change is confined to about 0.2 s after each boundary, and whether the old error was audible was not established (3.3.1).
- Speaker analysis corrected to the official Qwen frontend: periodic Hann, reflection padding 384, magnitude sqrt(real²+imag²+1e-9), 128 Slaney mel filters, natural log with 1e-5 floor. The upstream Swift helper used a Whisper-style normalized log-power representation. Numerical comparison with PyTorch/librosa over a deterministic 24 kHz fixture: shape 93×128, mean absolute error 0.00008452, maximum 0.004114 (FFT differences near the floor). This is frontend parity, not full model-output parity.
- Removed the upstream object-identity audio cache: freed array addresses can be reused for another speaker. Chatter alone caches conditioning by content, transcript, language and model.
- Recorded-voice conditioning combines all enabled takes with short silence and their exact transcripts. Each take's edges are trimmed first, ignoring bursts shorter than 60 ms, so no take ends in a long silence (`ReferencePreparation.trimmedForConditioning`, 3.3.1). Content/model/language keys and a bounded cache avoid repeating reference encoding. No takes are silently omitted.
- `wholeTextFirst` adds the reference's `non_streaming_mode` (the whole text in the prompt before the first frame), the official default for VoiceDesign and CustomVoice; designed voices use it with the VoiceDesign generation config (temperature 0.9, top-p 1.0). The upstream Swift port only fed text one token per frame.
- Types distinguish Base cloning from instruction-capable CustomVoice/VoiceDesign. Leading delivery notes are separated from words. Dialogue serializes frozen actor configurations as one durable job and returns post-pace turn timings.

Later upstream fixes, taken one by one; the rest of the copy stays at `01dec7c`:

- `dbe5eaac964e8257785f9d015c81f819a38016a8` (#281, "Update for mlx-swift / mlx-swift-lm", 2026-10-05), its three Qwen3TTS fixes, ported 2026-10-20 in 3.2.3. `ResidualVectorQuantization.decode` and the talker's interleaved mRoPE slice and squeeze (`codes[idx..<(idx + 1)].squeezed(axis: 0)`, `freqs[0..<1].squeezed(axis: 0)`) instead of indexing a scalar: MLX's scalar gather on a transposed view hands Metal empty index data, and with Metal API validation on (`MTL_DEBUG_LAYER=1`) 3.2.2 and earlier aborted in both places (`setBytes… bytes argument cannot be nil`). `streamingStep` evaluates its clipped output before returning it. The race that prevents cannot happen here, because all three callers evaluate each chunk on the engine worker before the next step; it is kept as upstream's guarantee for one more GPU sync per streamed chunk, about 1.7 ms per 0.8 s chunk in a debug build. Not taken: the `sending` annotations and `SendingBox`, the MLX-LM 3.32.3 bump and the MLXLMCommon removal (`92ca66cf`); Chatter stays on MLX 0.31.4 and MLX-LM 3.31.4. Checked on the installed models with fixed seeds and a synthetic `say` reference: mRoPE cos/sin (float32 and bfloat16; distinct, talker-shaped and 2-D positions), RVQ and codec decoding of fixed codes (whole, streamed, and step by step on transposed views), and whole and streamed generations for a Base clone, CustomVoice Ryan and VoiceDesign, 25 arrays and their token sequences, are bit-identical before and after. With validation on, the ported code runs all of them without error.

## Parity with the reference — 2026-11-12 (3.4.0)

The port was compared with the official PyTorch implementation (the vendored `Vendor/Qwen3-TTS` source at `022e286b`, Transformers 4.57.3, the same `speech_tokenizer` weights, and the official `Qwen/Qwen3-TTS-12Hz-1.7B-Base` weights for the talker) on Chatter's Scar (22.8 s) and JARVIS (33.3 s) recordings. Upstream weights and reference code are unchanged since the pins above: the four `mlx-community` repositories' `main` still point at the pinned revisions (last modified 2026-01-25), `QwenLM/Qwen3-TTS` is still at `022e286b`, and no newer open Qwen TTS model exists.

What matched already: the speaker embedding (cosine 1.000000 with PyTorch), and the talker and code predictor. Following the reference's own greedy codes, the port's first-codebook logits differ from PyTorch's by 0.005 on average (BF16 against float32), choose the same token at 360 of 361 frames, and the residual codebooks at 96 to 99 %, in both prompt layouts.

What did not, each also fixed upstream since Chatter's copy was taken (mlx-audio-swift #398, #369, #378, #371, #315; mlx-audio #897):

- **Reference encoder positions.** The tokenizer's encoder is Transformers' Mimi, whose rotary positions rotate the two halves of each attention head; the Swift port used Kyutai's interleaved pairs. A recording was therefore encoded to codes the model never saw in training: 23 % (Scar) and 24 % (JARVIS) of first-codebook codes agreed with PyTorch, 27 % and 26 % over all sixteen codebooks. With the right layout every code of both recordings agrees. (Transformers applies Mimi's 250-frame `sliding_window` only on its flash-attention path, so the reference encodes a whole recording with a plain causal mask, and so does the port.)
- **Decoder attention window.** The reference's decoder attends to 72 frames in every layer (`sliding_window`); the port attended to everything. Decoding the reference's own codes for each recording, the port's audio matched PyTorch's to 4e-6 relative error for the first 5.76 s and differed by 15 % (Scar) and 62 % (JARVIS) after it. With the window it matches to 1e-5 throughout, whole or streamed in 10-frame chunks. Whole passages were decoded after the whole recording, so every Balanced, Studio and saved passage of a long recording was affected: 71 of 96 JARVIS passages ended in sound rather than silence, against 8 with the window.
- **Valid length.** Upstream counted first-codebook codes above zero as the passage's length; code 0 is an ordinary code (the reference counts codes above −1). Each one cut 80 ms from the end. Removed.
- **Cold streaming decoder.** A streamed passage's decoder started from silence, where the reference decodes recording and passage together. The decoder's state after the recording is now kept with the voice's conditioning (`decoderState`) and every passage, streamed or whole, starts from it: the same audio as decoding them together, without decoding the recording again for each passage.
- **Sampler.** As in the reference, temperature is applied before top-k and top-p, the end of speech is a token like any other (upstream put it back after the cuts), and it cannot be drawn in the first two frames (`min_new_tokens`). Logits are sampled in float32.
- **Prompt type.** The float32 speaker embedding promoted a BF16 model's whole prompt, cache and every later frame to float32. Cast to the talker's type, the 1.7B model generates 33 frames a second on an M3 Ultra (2.6 times real time) instead of 14, and the 0.6B 8-bit model 44 instead of 33.

Chatter's own choices, measured with the corrected port (96 passages per setting and voice, on-device speech recognition and signal measures):

- **No top-p cut.** Chatter sampled recorded and built-in voices at top-p 0.8. Once the end of speech falls outside that nucleus it cannot be drawn, and the 0.6B model then loops in room tone to the frame budget: 5 of 96 JARVIS passages, with or without upstream's exemption, and none at top-p 1.0; word errors were the same (0.0 to 0.1 %). Temperature stays 0.7 for these voices: at the reference's 0.9 the 1.7B model made more word errors for Scar (1.3 % against 0.4 %).
- **Text-first prompt.** The reference's default layout for cloning lays the text over the recording's frames (`non_streaming_mode=False`); it ran on in 4 of 96 JARVIS passages against 2 for text-first at the same settings, so Chatter keeps text-first, which the reference also supports (`overlaysText` selects the other).
- **How a passage ends.** The model ends a passage by cutting to digital silence within about 5 ms, from whatever level the voice or its room tone has reached: sometimes on its last frame (1 to 14 of 96 passages by voice and model ended within 25 dB of their loudest speech), more often some tens of milliseconds before it. 3.4.0 generated the two frames that would have followed the end (`framesAfterEnd`), which made every passage end in silence by that measure, and was wrong: those frames are as often a 15 to 30 ms burst of noise standing in silence, up to 28 dB below the speech, and the burst was also taken for speech, so the room-tone fade started after the cut instead of covering it. Scar's recording has a background 27 dB below her speech, and its cut and the burst were heard as a click at the end of her clips. 3.4.1 generates no frames after the end and fades the last 60 ms of sound into the final silence wherever that sound stops (`PassageEnvelope.softensEnding`). Over 50 replies per voice, falls into digital silence that were cuts rather than fades went from 6 to 0 for Scar and from 17 to 11 for JARVIS (the 11 inside clips and at least 41 dB below his speech, where his clean recording simply goes quiet), and bursts from 7 to 0. The measure that passed 3.4.0, the level of a clip's last 20 ms, could not see either fault; `stops.py`'s successor in the test suite is `PassageEnvelopeDeliveryTests`.
- **1.7B for live speech.** For JARVIS the 1.7B model did not run on in 516 passages, with or without a top-p cut, and its duration for a sentence varied 3 to 5 % from draw to draw; without the cut the 0.6B model did not run on either (384 passages) and varied 5 %. For Scar, whose recording is conversational, both varied about 11 %. Word accuracy was the same. The 1.7B model is the one saved audio uses, so with it a reply sounds the same live as saved; seeding every passage from its voice and text removes the variation between runs for either model.

`chatter-tools lab <config.json>` reproduces these measurements: it generates the same passages under named variants of every switch above (`QwenGenerationOptions`, the decoder window, the encoder layout, the valid-length rule), encodes and decodes a recording, decodes given codes, and follows a given code sequence while recording the logits it would have chosen from.
