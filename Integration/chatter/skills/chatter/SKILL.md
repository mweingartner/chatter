Use the Chatter MCP tools. `chatter_voices` lists saved voice IDs; use the requested voice or the default when unspecified. The voice list reports `referenceMode`, `referenceSampleIDs`, total reference duration and each take's `included` flag. Omit `sampleID` to use the voice's configured set; all enabled recordings condition the same speaker. Use `sampleID` only when the user requests a single-take comparison. Preserve the user's requested wording. Read `chatter_status` if readiness is uncertain.

The current server exposes eight tools, including `chatter_capabilities` and `chatter_dialogue`; `chatter_speak` includes `language` and `instruction`. If the chat only exposes the older six-tool schema, its tool catalog is stale. Do not pretend missing parameters were sent. Check the installed transport with `scripts/chatter-tools.sh verify plugin --help`, and use a new chat after refreshing the plugin. A successful direct transport check does not prove the current chat has refreshed its tools.

Call `chatter_capabilities` and inspect each voice's `kind` and `supportsInstructions`. Recorded clones use Qwen Base and inherit delivery from the reference recordings; they do not implement instruction/tone conditioning. Do not promise optimistic or stern delivery on a clone. Preserve the requested speaker and explain the limitation. Built-in and designed voices accept `tone`, `language`, and natural-language `instruction` separately from spoken text. Never insert Qwen control tokens into the text. Qwen handles expression directly. Chatter does not run Ollama or automatically annotate speech. Supply delivery direction through `instruction`, leaving `text` as the exact spoken words.

Send names and acronyms normally: saved pronunciation mappings apply automatically. Use `chatter_speak` with voice, text, pace (0.5–2), mode (play/save), optional quality, tone, language, and instruction. Save uses full-precision native 24 kHz/24-bit PCM. Play speaks on the host Mac. Responsive and Balanced use the same 0.6B 8-bit model for recorded voices; Studio uses 1.7B BF16. Built-in/designed voices use their 1.7B BF16 model at every level. Quality changes buffering for those voices. Discover exact tone IDs with `chatter_tones`. Use a stable requestID for identical retries.

For scripts with multiple actors use `chatter_dialogue`: `cast` maps actor names to saved voice IDs; `turns` is an ordered array of `{actor,text,tone?,language?,instruction?}`. Set gapSeconds (0–10), pace, mode and optional quality. `mode: "play"` speaks on the host: Responsive streams chunks within each turn, while Balanced/Studio buffer passages. `mode: "save"` always uses Studio. One dialogue occupies one FIFO position and produces one WAV. Limits: 20 actors, 500 turns and 100,000 spoken UTF-8 bytes. Check each actor's voice capabilities. Completed jobs include dialogueTiming for editor alignment. Designed voices can vary between generations; for a consistent character use a recorded profile created from an approved design preview.

Submission acknowledges a durable FIFO queue entry, not completed audio. Poll `chatter_job` at sensible intervals until `completed`, `failed`, or `cancelled`. Report a failure accurately. Use `chatter_cancel` only when the user wants that job stopped. A busy engine can accept queued work; do not submit duplicate speech while waiting.

For a completed saved file, return its local path when the client shares the host filesystem. For a LAN client, the returned `audioURL` is relative to CHATTER_URL and requires the same bearer token. Never print or embed tokens in links. Download through an authenticated client if the user needs a local copy. Do not call an inaccessible remote host path a local file.

## Video narration

When a prompt combines **Chatter and Remotion**, read [the Remotion workflow](references/remotion.md) and the installed Remotion skill. It covers research-to-storyboard requests, per-scene speech, resumable handoff, local assets and audio-derived frame timing. Use Chatter as the requested narrator even if generic Remotion voiceover examples name another provider. Preserve the user's exact personas and content scope.

For a video voice track, use `mode: "save"`; this produces studio-quality mono 24 kHz / 24-bit PCM WAV. Use one request per scene or narration cue when the script is already divided that way. Keep the chosen voice, tone and pace consistent unless the script or user calls for a change. Include only spoken words in `text`, excluding scene headings and production directions. Use a stable unique `requestID` per logical cue and reuse it for identical retries; give revised wording or delivery a new ID. Multiple scenes may be queued; do not assume they run concurrently.

Poll each job to `completed` and retain a handoff record containing the scene/cue name, job ID, text, voice, tone, pace, absolute WAV path and measured duration in seconds. Derive editor timing from this duration, not the text length. Preserve the original saved WAVs for reuse. Do not claim the video is narrated just because audio is queued or saved.

Retain the accepted language, instruction, quality, voice configuration, reference sample IDs and warnings with each track. A recorded `tone` is the requested preset, not proof it was supported or audibly achieved. Dialogue tracks also need their cast, per-turn controls and actual `dialogueTiming`. Chatter already applies pace, sentence pauses and short passage-edge fades; do not apply pace or additional sentence fades again in the editor. Older exported files are unchanged by app updates; regenerate affected cues with new request IDs when an engine fix is needed.

When the user asks to use the narration in Borumi and Borumi tools are available:

1. Call Borumi `get_guides` without arguments at the start of its connection, then retrieve the required project-edit, media-import and timeline guides once. Follow the installed tool schemas; these can evolve independently of Chatter.
2. Resolve the requested project with Borumi tools. Use an isolated project edit transaction. Import the completed local WAV with `import_media` and poll its status at the recommended interval. Use the returned Media ID for timeline placement; never pass a file path as a Media ID.
3. Place the narration at the intended scene/cue time using the applicable Take/audio segment schema and its measured duration. A new empty project needs a scene before a Take can be placed; follow the scripting guide if creating one. Inspect the new audio segment's processing: for already synthesized studio narration, disable automatic voice enhancement unless the user requests it, using the audio-update guide. Do not replace existing narration or change visuals unless the user's request includes those edits. Synchronize separate audio and screen content under Borumi's synchronization guide when needed.
4. Reread and verify the staged timeline before committing. State exactly which scene or cue was added and its duration. If the edit fails, abort the transaction and keep the original Chatter WAV available.

If the client and editor run on different machines, first retrieve the WAV to the editor's filesystem through the authenticated audio endpoint. If Borumi is unavailable, return the completed WAV and timing record without claiming an import. Other editors can consume the same WAV and timing record; no Borumi-specific audio format is required.

Voice setup, batch audio import and guided microphone recording happen in Chatter's Your voices panel. Tone cues guide delivery with variable strength; do not promise a particular emotional intensity or approved voice likeness. The model uses local reference adaptation; do not describe it as a completed fine-tuning run. Do not claim voice resemblance has been approved unless the user has assessed it.
